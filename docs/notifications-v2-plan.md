# Notifications v2 + Sharing plan

Status: **proposed 2026-09-07, signed off same day, and built.** V2.0, V2.1, V2.2, V2.3 (minus
§5.5's Android shortcuts and §5.3's relevance scoring, both cut — see below) and the attribution
half of V2.5 shipped 2026-09-07. **V2.4 (Live Activity) is deliberately not built** — §9 open
question 1 recommended option (b), hold until the app is out of TestFlight, and that stands.

What's in V2.5 and what isn't: §6.1 (share consolidation), §6.3's link-gap closes (`/post/:id` web
page, AASA/intent-filter additions) and its attribution params shipped. §6.2's template OG images
shipped as four tier-coloured PNGs generated by `scripts/generate-og-templates.js` (no
`sharp`/`jimp`/`canvas` dependency — `website/` stays dependency-free per the decision below) —
they differentiate by tier colour, not full per-game artwork; `@vercel/og` is still explicitly
gated on evidence, per the plan. §6.4's image cards (`GameShareCard`/`AchievementShareCard`/
`ResultShareCard`) are **not built** — real design/composition work, cut from this pass rather than
rushed; add to quick-wins.md or re-propose as its own slice.

§5.5 (Android per-conversation shortcuts) is cut: there's no Expo-managed API for
`ShortcutManager` without a custom native module, and AGENTS.md's native-target caution (the
1077/1079 crash history) argues against adding one for a "cheap once channels exist" nice-to-have.
§5.3 (relevance score / notification summary tuning) is cut: Expo's push API has no exposed
`relevanceScore` field to set it through, and `interruptionLevel: passive` (already shipped, P1)
covers the same "don't fight the OS summary" goal for low-tier pushes.

Scope: two halves of the same problem, which is why they share a doc.

1. **Notifications v2** — what the notification system doesn't cover yet (the whole social
   surface), what it covers with copy that's too thin to act on, and what the platform can do in
   2026 that [notifications-plan.md](notifications-plan.md) §8 explicitly deferred in August.
2. **Sharing v2** — what a Smashio link actually looks like when it lands in a WhatsApp thread,
   and every place the app could hand someone a link but doesn't.

**Decisions taken 2026-09-07**, before sign-off, on the four questions this doc opened with. They
are applied inline below; §9 records them and what each one changed.

1. **OG images: templates now, `@vercel/og` later.** `website/` stays dependency-free for now.
2. **F6 `followed_posted`: ship**, with a 2/day cap and its own preference category.
3. **I1 `replacement_found`: cut.** Moved to §8.
4. **No avatars in notifications.** No iOS Notification Service Extension, so no custom native
   target in this plan. Actor identity is done in the inbox, where it is free.

Read [notifications-plan.md](notifications-plan.md) first — v1 is fully shipped (P0–P3) and this
doc assumes its architecture, tiers and principles rather than restating them. Read
[social-plan.md](social-plan.md) §17 before touching anything in §2 below; the feed's scope is
settled and this doc does not widen it. Read [gtm-plan.md](gtm-plan.md) §3 (G3, G11) before §6 —
the share-link gaps there are the same gaps.

## 0. Where we actually are

This is not a greenfield area. v1 shipped hard and the audit below is the starting line, not the
problem statement.

**22 notification types are live**, all flowing through one pipeline: a SQL trigger resolves
recipients and writes `notifications` rows transactionally with the event, then `notify_push`
hands the row ids to the `push-dispatch` edge function, which renders copy in
[format.ts](../supabase/functions/push-dispatch/format.ts), sends via Expo, and stamps
`title`/`body`/`sent_at` back.

| Area | Types shipped |
|---|---|
| Roster | `join_request` (+coalesced), `join_decision` (approved/rejected/removed), `player_left`, `game_full`, `game_invite`, `spot_declined`, `hold_nudge`, `hold_auto_released` |
| Game changes | `game_cancelled`, `game_rescheduled`, `details_changed`, `booking_verified` |
| Time-based | `reminder_24h`, `reminder_2h`, `post_game_rate`, `post_game_attendance`, `nudge_underfilled`, `nudge_pending` |
| Discovery | `alert_match` |
| Chat | `message` (+coalesced) |

Also live: seven preference categories + quiet hours (`notification_prefs`), five Android
channels, iOS `interruptionLevel` per tier, per-recipient timezone, app-icon badge, an in-app
inbox with Realtime, tray action buttons (Approve/Decline), Expo receipt handling with dead-token
pruning, and a retry sweeper.

**So v2 is not "make notifications work". It's four specific things:** cover the surface that has
zero notifications, make the copy carry enough that the notification itself is useful, use the
2026 platform features v1 deferred, and fix sharing so a link is worth sending.

## 1. What's missing — findings

### 1.1 The entire social surface has zero notifications

Five tables shipped between 2026-09-01 and 2026-09-02 with **no notification trigger on any of
them**:

| Table | Migration | Notification triggers |
|---|---|---|
| `posts` | [20260901040000_posts_feed.sql](../supabase/migrations/20260901040000_posts_feed.sql) | none |
| `post_replies` | [20260901100000_feed_v3_replies_reactions.sql](../supabase/migrations/20260901100000_feed_v3_replies_reactions.sql) | none |
| `post_reactions` | same | none |
| `follows` | [20260901010000_follows.sql](../supabase/migrations/20260901010000_follows.sql) | none |
| `achievement_awards` | [20260901030000_achievement_awards.sql](../supabase/migrations/20260901030000_achievement_awards.sql) | none |

Verified by grepping `enqueue_notifications`/`notify_push` across all migrations — the only files
that call them are the game/chat/roster ones. This is the single biggest gap. A player posts
"looking for a fourth on Thursday", three people reply, and **the poster is never told**. The feed
is a write-only surface for anyone who doesn't reopen the tab.

This is also the highest-leverage gap for retention: the feed is the only surface where a
notification can pull someone back who has no game booked.

### 1.2 `chat_mention` was planned Critical and never shipped

[notifications-plan.md](notifications-plan.md) §4E lists E3 `chat_mention` as a **Critical**-tier
event with its own copy. It is not in `format.ts`, not in `CHANNEL_FOR_TYPE`, and not in
`index.ts`. `messages.mentions` still only gates *whether* a push fires when
`chat_prefs.level = 'mentions'` — being named by the host in a game chat produces byte-identical
copy and priority to any other chat line. The one place the app knows something is definitely
addressed to you, and it's indistinguishable.

### 1.3 Waitlist promotion borrows someone else's copy

[waitlist.sql](../supabase/migrations/20260830235900_waitlist.sql) auto-promotes the head of the
queue by flipping `game_players` to `approved`, deliberately reusing the existing pipeline. The
result is correct plumbing with the wrong words: the player gets `join_decision`'s "You're in —
7:00 pm", identical to a host manually approving them. It never says *a spot opened up and you got
it because you were next in line*, which is the whole reason they'd care and the whole reason they
should reply fast. Needs a `waitlist_promoted` type, not a new trigger.

### 1.4 The inbox is a stripped-down copy of the push

[ui/app/notifications.tsx](../ui/app/notifications.tsx) renders `title` / `body` / `timeAgo` and an
unread dot. That's it. No avatar of the actor, no per-type icon or colour, no date grouping, no
filtering, no inline actions — the tray has Approve/Decline buttons that the in-app inbox
**doesn't**, which is backwards. Twenty rows of identical grey two-line text is not scannable, and
the inbox is where notifications go to be recovered after being swiped away.

### 1.5 Copy is one line, and sometimes the line that matters is missing

The bodies are good (§4 of v1 did real work here) but they're built for a lock screen glance and
reused verbatim everywhere. Specific weak spots:

- **`join_request` doesn't say who the person is.** "{actor} wants to join · {sport} · {venue},
  {time} · 2 of 4 spots filled." The host's actual decision needs *tier, reliability, games
  played* — the three things on the player card. Approving from the tray without them is a coin
  flip, which undercuts the tray action buttons that shipped in P3.
- **`alert_match` doesn't say why you got it.** It names the game but never the alert that matched
  it, so it reads as spam from the app rather than a thing you asked for.
- **`game_cancelled` ends the relationship.** "Your spot is released" and nothing else. This is
  the highest-intent moment in the app — someone had that slot in their calendar — and it offers
  no next game.
- **`post_game_rate` doesn't name anyone.** "Rate the 3 players" — naming them is what makes it
  feel like a small social obligation rather than a chore.
- **No explanatory second line anywhere.** Every notification is title + one body. iOS and Android
  both expand to multiple lines on long-press/pull-down; we send nothing extra to fill it.

### 1.6 No rich notifications, no Live Activities

v1 §8 ruled both out, correctly, for August:

> **Rich media pushes** (avatars, images in the notification). Needs a Notification Service
> Extension on iOS; not worth it before store launch.

Two things changed. First, we're now on **Expo SDK 57**
([ui/package.json](../ui/package.json)), and `expo-widgets` — iOS home-screen widgets and Lock
Screen Live Activities as React components, no SwiftUI — [went stable in SDK
56](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo). Second, an NSE is now a
`npx create-target` + config-plugin job rather than a hand-rolled Xcode target.

The second of those was **considered and rejected on 2026-09-07** — see §5.1. Cheaper to build is
not the same as cheap to ship, and the cost that mattered was the native-target risk, which hasn't
moved. The first is still open; see §9.

A badminton game is close to the canonical Live Activity: fixed start time, a countdown that
matters, a roster number that changes, and a venue you're travelling to. "Starts in 47m · Court 3
· 4 of 4 in" sitting on the lock screen from T-4h is worth more than both reminder pushes
combined, and it's the single most modern-feeling thing the app could ship.

### 1.7 Sharing findings

**Four separate implementations of "share a game", three of them inline.**
[ui/lib/share.ts](../ui/lib/share.ts) has `shareGame`, but
[wizard.tsx:967](../ui/app/wizard.tsx:967) re-implements it inline with different copy,
[venue/[id].tsx:46](../ui/app/venue/[id].tsx:46) has its own `shareVenue`, and
[ReservedSpots.tsx:206](../ui/components/ReservedSpots.tsx:206) has its own for invites. Four
places to fix any share bug.

**Sport is hardcoded in the share copy — an AGENTS.md rule violation.** `shareGame`,
`copyGameLinkForWhatsApp`, `shareReferral` and the wizard's inline share all say the literal word
"badminton". The rule is that sport is a config/data concern; the share sheet is the one string a
non-user reads first.

**Every shared link produces the same preview image.** [website/api/game/[id].js:72](../website/api/game/[id].js:72)
sets `og:image` to a static `https://smashio.com.au/assets/og-image.png` — the same 121 KB file for
every game, every venue, every club. The page body is genuinely per-game (real title, description,
countdown chip, tier colour, and the OG title/description are dynamic) but the picture — the part
WhatsApp actually renders at 1200×630 — is generic.

**Feed posts are unshareable.** `ui/app/post/[id].tsx` exists in the app; `website/api/post/` does
not, and `vercel.json` has no `/post/:id` rewrite. Nothing produces a post link, and if it did it
would 404.

**Deep-link coverage lags the site.** [apple-app-site-association](../website/.well-known/apple-app-site-association)
and the Android `intentFilters` in [app.config.js](../ui/app.config.js) both list `/game/*`,
`/venue/*`, `/player/*` only. `/club/:slug` and `/sydney` are server-rendered on the site and
**open in a browser instead of the app**, even when the app is installed.

**The one genuinely good share asset is used on exactly one screen.**
[ShareCard.tsx](../ui/components/ShareCard.tsx) renders a designed square/story image card via
`react-native-view-shot` + `expo-sharing`, with a format picker. It's wired only to the profile
screen. A game, an achievement, a post-game result and a club all deserve the same treatment.

**`share.ts` still imports its type from `mockData`.** `import type { Game } from "./mockData"` —
harmless, but AGENTS.md says no mocked data remains, and this is the last thread.

## 2. Principles for v2

v1's seven principles stand. Three additions:

8. **A notification explains itself.** Body line one says what happened; the expanded/second line
   says *why you got it and what happens if you ignore it*. The lock-screen glance and the
   pulled-down expansion are two different reads, and we currently only write the first.
9. **Show the person, not the event.** Anything caused by a human — join request, reply, mention,
   follow, reaction — carries that person's avatar and name. Anything caused by the system doesn't
   pretend to.
10. **The share is the product's front door.** A link is seen by people who don't have the app.
    Every shared link renders a real preview of the real thing, and lands in the app when the app
    is installed.

## 3. New notification events

Copy follows v1's deterministic-variant pattern (`pick(variants, seed)`), and interpolates from
`push_game_summary` / `push_actor_name`. **`{expand}` is the new second line** (§4.1) — shown when
the notification is expanded, in the inbox row, and nowhere else.

### F. Social — the gap from §1.1

| # | Event | Trigger | To | Title / body / expand | Tap | Tier |
|---|---|---|---|---|---|---|
| F1 | **post_reply** | `post_replies` insert | post author, minus self | "{actor} replied" / reply text, 140 / "On your post: '{post excerpt}'" | `/post/:id` | Normal |
| F2 | **post_reply (coalesced)** | ≥3 replies in 15 min | post author | "{n} replies on your post" / "'{post excerpt}'" | `/post/:id` | Normal |
| F3 | **post_reaction (coalesced only)** | ≥1 reaction, batched hourly | post author | "{actor} and {n} others backed your post" / "'{post excerpt}'" | `/post/:id` | Low |
| F4 | **reply_to_thread** | reply on a post you also replied to | prior repliers, minus author, minus self | "{actor} joined a thread you're in" / reply text | `/post/:id` | Low |
| F5 | **new_follower** | `follows` insert | followed | "{actor} followed you" / "{tier} · {n} games played · plays around {suburb}" / "Follow back to see their games in your feed." | `/player/:id` | Low |
| F6 | **followed_posted** | `posts` insert by someone you follow, type `looking_for_players` only | followers, capped 2/day/user | "{actor} needs players" / "{sport} at {venue}, {time} · {spots} spots" | `/post/:id` | Low |
| F7 | **achievement_earned** | `achievement_awards` insert | earner | "{achievement_name} unlocked" / "{achievement_blurb}" / "Tap to see it on your card, or share it." | `/profile` + share sheet | Low |

Notes that matter:

- **F3 is coalesced-only by design.** One push per reaction is the fastest way to make people
  disable the category. An hourly batch per post is the floor.
- **F6 is the one that needs a hard cap and a kill switch. Approved 2026-09-07 on exactly those
  terms.** It is the only push in the whole system triggered by someone else's routine activity
  rather than by something involving you. Cap 2/day/user, `looking_for_players` only (never
  `question`), and it gets its own preference category rather than sharing one — someone who
  follows 40 players must be able to turn off F6 while keeping F1. The cap is a build requirement,
  not a tuning knob: shipping F6 without it is shipping a different feature than the one approved.
- All seven gate on a new `social` preference category, except F6 which gets `social_activity`.
- The "Never notified" list from v1 §4 extends: nobody is notified that they were *un*followed, or
  that a reaction was removed, or that their post was reported.

## 4. Making the content explanatory

### 4.1 The `expand` line

Add a third rendered string alongside `title` and `body`. `PushBody` becomes
`{ title, body, expand? }`. It is:

- sent as `subtitle` on iOS (renders under the title, visible when expanded),
- sent in `data.expand` and rendered as a third line in the **inbox row** on both platforms,
- **never counted toward the 140-char body budget** — it exists precisely because the body is
  rationed.

Android has no direct subtitle equivalent in the Expo push API; there, `expand` is appended to the
body behind a line break, which Android's own expand gesture reveals. Both platforms then show the
same two-part read, by different mechanisms.

Rules for writing one, to keep it from becoming filler:

- It answers **"why am I seeing this?"** or **"what happens if I do nothing?"** — never restates
  the body.
- If neither question has an interesting answer, there is no `expand` line. `reminder_2h` doesn't
  need one.
- Same Australian voice as the rest of the app ([CLAUDE.md](../CLAUDE.md) copy rules): contractions
  fine, no em dashes, plain and warm.

Examples across existing types:

| Type | Existing body | New expand line |
|---|---|---|
| `join_request` | "{actor} wants to join · {sport} · {venue}, {time} · 2 of 4 filled" | "{tier} · {n} games played · {reliability} reliability. Approve or decline right here." |
| `alert_match` | "{venue}, {time} · {tier} · ${per_player}" | "Matches your '{alert_name}' alert. Turn it off in Discover any time." |
| `game_cancelled` | "{host} cancelled {sport} at {venue}, {time}. Your spot is released." | "You haven't been charged anything. There are other games on near you, have a look." |
| `nudge_underfilled` | "Your game is tomorrow at {time}. Share it to fill up." | "{n} of {max} in. Games that fill up usually do it in the last day." |
| `post_game_rate` | "Rate the {n} players from {sport} at {venue}." | "{name1}, {name2} and {name3}. Ratings stay private and take about 20 seconds." |
| `booking_verified` | "{host} uploaded the booking for {venue}, {time}." | "The court's locked in, so this one's not getting cancelled for a booking clash." |
| `game_full` | "{n} of {n} in for {sport} · {venue}, {time}." | "Requests are closed. You can still add a reserved spot for a mate." |

### 4.2 `join_request` gets the player card

The single most valuable copy change, because P3 already shipped tray Approve/Decline buttons and a
host currently uses them blind. `push_actor_name` grows into `push_actor_summary(p_profile_id,
p_sport_id)` returning `display_name, tier_label, games_played, reliability_label, suburb,
avatar_url`. Everything in it is already visible on the player card to any authenticated user, so
this exposes nothing new — it just moves it to where the decision is made.

Same call feeds F1/F4/F5's avatars (§5.1) and G1's mention copy.

### 4.3 Notification-type taxonomy for the inbox

Adding social types roughly doubles the type count, and §1.4's flat grey list doesn't survive that.
Each type gets, in `format.ts` alongside its copy so there's still one source of truth:

- an **icon** (from the existing icon set),
- an **accent colour** — reusing the tier palette (accent for roster wins, amber for nudges, red
  for cancellations, neutral for social),
- a **grouping key** — Today / Yesterday / This week / Earlier.

## 5. 2026 platform capabilities

Ordered by value per unit of risk. Each is independently shippable.

### 5.1 Avatars in the notification — **cut 2026-09-07**

Proposed as an iOS Notification Service Extension (`npx create-target`, ~30 lines of Swift that
fetch an avatar and attach it) so a join request would show the requester's face. **Not doing it.**

The reason is [store-readiness-plan.md](store-readiness-plan.md) and the AGENTS.md rule it feeds:
builds 1077 and 1079 passed CI and then crashed on launch with a missing Swift symbol, and a green
iOS build does not prove the app launches. An NSE would be the project's first custom native
target, on the only platform that has actually shipped, to add decoration to a notification that
already reads fine. Wrong trade while the app is in TestFlight.

**Actor identity moves to the inbox instead** (§4.3), where an avatar costs nothing — it is a
React component reading a URL the row already carries. `push_actor_summary` (§4.2) is unaffected
and still ships; it was always about the *copy* carrying tier and reliability, not the picture.

Two consequences worth naming rather than discovering later:

- **iOS Communication Notifications die with this.** `INSendMessageIntent` — which renders a chat
  push in the system's messaging style with the sender's avatar and lets a user pin a game chat in
  a Focus mode — needs the same target. Genuinely nice, genuinely not worth a launch crash.
- **Android avatars are still free and still not happening.** Android shows an image from a URL in
  the existing payload with no native code at all. Rejected anyway, for consistency: a
  notification that has a face on one platform and not the other is worse than one that has no
  face on either, and it doubles the copy-review surface for no product gain.

### 5.2 Live Activity for the next game (iOS)

The headline feature. `expo-widgets`, stable since SDK 56, we're on 57.

- **Starts** when the user is approved for a game starting within 8 hours, or at T-8h for a game
  they're already in; ends at `ends_at + 30 min`.
- **Shows**: countdown to start, venue + suburb, court label, "{n} of {max} in", verification tick.
- **Updates remotely** via ActivityKit push tokens (`instance.getPushToken()`,
  `addPushToStartTokenListener()`) — the existing `push-dispatch` gains a branch that updates the
  activity instead of sending a banner when the recipient has a live activity for that game. A
  roster change or a court change updates the lock screen silently rather than firing another push.
  **This is what makes it worth building**: it lets us *remove* pushes, not add them.
- Deep-links into `/game/:id` on tap.
- iOS only, dev builds only, four-hour dismissal window on the `after(date)` end policy.
- Android's rough equivalent is an ongoing notification with a chronometer. Cheap, worth doing in
  the same slice for parity, and it needs nothing native.

> **This inherits §5.1's problem and needs its own call — see §9 open question 1.** `expo-widgets`
> does not write Swift, but it still produces a **widget extension target** in the iOS build, so
> the "green build does not prove it launches" risk that killed the NSE applies here too, at
> larger scale — a Live Activity is a much bigger surface than a fetch-and-attach extension.
> Cutting the NSE and keeping V2.4 unexamined would be inconsistent. The counter-argument is that
> this one is worth real risk: it is the only item in the doc that *removes* notifications rather
> than adding them, and it is the single most modern-feeling thing the app could ship. Decide it
> deliberately, not by inheritance.

### 5.3 Notification summary and delivery timing

iOS's scheduled summary already exists at OS level; we currently opt every notification into
immediate delivery by tier. Low-tier events (F3, F5, F6, `alert_match`) should set
`interruptionLevel: passive` **and** the relevance score so they sort sensibly inside a summary
rather than fighting it. Zero product surface, small payload change, meaningfully less annoying.

### 5.4 Inline reply for chat (both platforms)

**The Reply button already exists and does nothing.**
[ui/lib/notifications.ts:210](../ui/lib/notifications.ts:210) is explicit about it:

> `// P3 chat reply action (E1): placeholder for now. Full implementation requires a compose UI.`

The `chat_actions` category is registered on both platforms with a `reply_chat` action, but it has
no `textInput`, sets `opensAppToForeground: true`, and the handler just navigates to `/chat/:id`.
A button labelled "Reply" that opens the app is worse than no button — it costs a tap and teaches
people the action is fake.

Real version, and it needs **no native target**, which is why it survives the §5.1 decision: add
`textInput: { submitButtonTitle, placeholder }` to the category, flip `opensAppToForeground` to
false, read `response.userText` in the existing response handler, and insert into `messages`.
`expo-notifications` covers `UNTextInputNotificationAction` and Android `RemoteInput` behind that
one option. All JS.

With §5.1 cut, this is the substance of V2.3.

### 5.5 Android per-conversation shortcuts

`ShortcutManager` conversation shortcuts let an Android user pin a specific game chat to the top of
their shade and give it its own bubble. Cheap once channels exist, and channels already do.

### 5.6 Home screen widget — "your next game"

Falls out of `expo-widgets` almost free once 5.2 is built (same target, same data). Not a
notification, but it's the same surface and the same slice.

## 6. Sharing v2

### 6.1 Consolidate first

One module, `ui/lib/share.ts`, exporting `shareGame`, `shareVenue`, `sharePost`, `shareClub`,
`shareProfile`, `shareAchievement`, `shareInvite`, `shareReferral`. Delete the three inline
implementations (§1.7). Every one takes the sport from data, never a literal. Drop the `mockData`
type import.

### 6.2 Dynamic OG images — the WhatsApp fix

This is what the user actually sees. Requirements, per current WhatsApp behaviour: **1200×630,
under 300 KB, PNG or JPEG, key content inside the centre 80%** (WhatsApp centre-crops anything off
1.91:1, and drops the image entirely above its size limit — at which point the preview silently
degrades to a text-only card).

`website/api/og/game/[id].js` renders a real card per game: sport, venue + suburb, day and time,
tier chip in its tier colour, spots-left count, host's first name, and the brand mark on the dark
lime-accented ground `index.html` already uses. Same for venue, club, and player.

**Decided 2026-09-07: templates now, `@vercel/og` later.** `website/` has no `package.json` and no
build step, by design, and that property is worth keeping until the value is proven rather than
assumed.

**Now (V2.0):** pre-render a small set of template PNGs — sport × tier, roughly eight files — and
pick one at request time from the data `game_preview` already returns. No per-game text, but a
badminton intermediate game stops looking identical to a club page, and it ships in an afternoon
and improves **every link already sent**, since the OG URL is resolved fresh on each share.
Templates live in `website/assets/og/`, named `og-{sport}-{tier}.png`, each 1200×630 and held
under 300 KB.

**Later (V2.5, on evidence):** `@vercel/og` (Satori) for the real per-game card, gated on the
share-attribution numbers from §6.3 showing that shared links actually convert. That is one
`package.json` with a single dependency; Vercel installs it for the functions, the static HTML is
untouched, and there is still no bundler. Revisit rather than pre-commit.

Rejected: rendering the card in-app with `ShareCard` and uploading to Storage. No website deps, but
it only covers games created after it ships, costs a Storage write per game, and leaves every
existing link generic — which is the specific thing templates fix for free.

`game_preview` needs one additive column for this: `spots_left`. It's not PII (it's on the public
card already) and "2 spots left" is the line that makes someone tap.

Also worth setting while we're in the head: `og:image:alt`, `og:site_name`, and per-page
`og:type` (`article` for posts) — small, and it's what separates a preview that looks
intentional from one that looks scraped.

### 6.3 Close the link gaps

- **`website/api/post/[id].js` + a `/post/:id` rewrite.** The app has the screen; the web has
  nothing. A shared post currently 404s.
- **AASA + Android intent filters gain `/club/*`, `/post/*` and `/sydney`.** Three site surfaces
  that open a browser today even with the app installed. One-line change in two files; note the
  AASA is cached aggressively by Apple, so it wants to ship ahead of the app build, not with it.
- **Every share link carries UTM-style attribution** (`?s=<kind>&r=<sharer_id>`), reusing
  [lib/referral.ts](../ui/lib/referral.ts)'s existing capture. Right now `shareReferral` is the
  only link that credits anyone, so we can't tell which share surface actually acquires users —
  [gtm-plan.md](gtm-plan.md) §3's whole measurement problem in one line.

### 6.4 Image cards beyond the profile

`ShareCard` becomes `ShareCard` + `GameShareCard` + `AchievementShareCard` + `ResultShareCard`,
same square/story format picker, same `view-shot` → `expo-sharing` path.

- **Game** — offered on the wizard success screen and the host's share chip, alongside the link
  (link for WhatsApp, image for Stories).
- **Achievement** — the natural pairing with F7, and the only notification in the system whose
  correct call to action is "show someone".
- **Post-game result** — from `/post-game/:id`, once attendance is marked.

`react-native-view-shot` 5.1.0 is already in the tree, so this is composition work, not
integration work.

### 6.5 Share copy, written properly

Current: `Join me for badminton at {venue} · {date} {time}` — hardcoded sport, no spots, no hook,
and on Android the URL is welded into the message so it renders twice in some targets.

Proposed, sport interpolated:

> Come play {sport} at {venue}, {day} {time}. {n} spots left — grab one here:

with the URL passed as the separate `url` field on iOS and appended once on Android (the existing
platform split is right, keep it). WhatsApp then renders the text plus one preview card, which
after §6.2 is a real picture of the actual game.

## 7. Phasing

Each phase is independently shippable and independently valuable.

**V2.0 — the holes (~2 d).** G1 `chat_mention`, H1 `waitlist_promoted`, share consolidation
(§6.1), sport de-hardcoding, AASA/intent-filter additions, `/post/:id` web page, template OG images
(§6.2 option a). No new tables. Everything here is a bug in something already shipped.

**V2.1 — social notifications (~3 d).** F1–F7, the `social` and `social_activity` preference
categories, F6's 2/day cap, F2/F3 coalescing, inbox routing to `/post/:id` and `/player/:id`. The
retention work.

**V2.2 — explanatory copy + inbox (~2.5 d).** The `expand` line end to end (§4.1),
`push_actor_summary` (§4.2), rewritten copy for all 22 existing types, inbox taxonomy — icons,
colours, date grouping, actor avatars, inline actions matching the tray (§4.3). No new events. With
§5.1 cut this is now the **only** place actor identity gets a face, which raises its value.

**V2.3 — notification actions (~1.5 d, was ~3 d).** Real inline chat reply (§5.4 — the shipped
Reply button is a placeholder), Android conversation shortcuts (§5.5), relevance and summary tuning
(§5.3). No NSE, no Communication Notifications, **no native target** — the phase is now entirely
JS and config, which is most of why it shrank.

**V2.4 — Live Activity + widget (~4 d). Blocked on §9 open question 1.** §5.2 and §5.6, plus the
Android ongoing notification. The most visible item in the doc and the most likely to slip;
deliberately last, and not startable until the widget-extension risk is settled the way the NSE's
was.

**V2.5 — image cards + dynamic OG (~2 d).** Share image cards for game/achievement/result, share
attribution params (§6.3), and `@vercel/og` **only if** the attribution numbers justify it.

Total ~13 days as decided, down from ~17. **If only one phase ships: V2.1.** The feed is live and
silent, and that's the loudest gap in the app.

## 8. Not doing

Carrying forward v1 §8 (no email/SMS, no notifying a ratee, no per-notification snooze, no
waitlist-invite-on-leave), plus:

- **Notifying on `question` posts.** F6 covers `looking_for_players` only. A question is not an
  event.
- **Follower-graph fan-out beyond F6.** No "someone you follow joined a game", no "someone you
  follow got an achievement". That's a social network's notification model and this is a
  player-matching app.
- **Digest email or a weekly wrap.** Same reason as v1.
- **Android Live Activities.** No real platform equivalent; the ongoing notification in V2.4 is the
  honest version.
- **Notification-triggered AI summaries** of a chat or a feed thread. `ai-proxy` could, and it
  would be a bad idea at this scale.
- **In-app share to a specific contact.** The OS share sheet is better than anything we'd build.
- **Avatars/images in notifications, on either platform.** Cut 2026-09-07; reasoning in §5.1. Takes
  iOS Communication Notifications with it.
- **`replacement_found`** — offering the ex-roster of a cancelled game another game that night.
  Cut 2026-09-07 as premature rather than wrong: it optimises a path few people hit at private-beta
  volume, and a same-night replacement inside someone's alert radius has to actually *exist* for
  the notification to be anything but a reminder that it doesn't. Revisit when Sydney game density
  supports it — at which point it likely belongs in [discover-plan.md](discover-plan.md) as
  matching logic rather than here as a notification. The `game_cancelled` dead end it was meant to
  close is handled for now by that type's `expand` line (§4.1).

## 9. Decisions taken, and what's still open

### Decided 2026-09-07

| # | Question | Decision | What it changed |
|---|---|---|---|
| 1 | `package.json` in `website/` for `@vercel/og`, template PNGs, or app-side generation? | **Templates now, `@vercel/og` later on evidence** | §6.2 rewritten. V2.0 gains ~8 template PNGs; V2.5 drops from 2.5 d to 2 d and `@vercel/og` becomes conditional on §6.3's attribution numbers. |
| 2 | Ship F6 (`followed_posted`) at all? | **Ship, with 2/day cap and its own category** | §3F note hardened — the cap is a build requirement, not a tuning knob. |
| 3 | Is I1 (`replacement_found`) a notification fix or a discovery feature? | **Cut for now** | §3I removed, entry added to §8 with the revisit condition. `game_cancelled`'s `expand` line rewritten, since it had been promising exactly what I1 would have delivered. |
| 4 | Does an NSE justify the project's first custom native target? | **No. No avatars in notifications, either platform** | §5.1 becomes a cut with reasoning. iOS Communication Notifications go with it. V2.3 shrinks from ~3 d to ~1.5 d and becomes fully JS. §4.3's inbox avatars absorb the actor-identity job. |

Net effect: ~17 d → ~13 d, and no phase in the plan now requires a native target — except V2.4,
which is why it's the one thing still open.

### Still open

1. **Does decision 4's reasoning also kill V2.4's Live Activity?** `expo-widgets` writes no Swift,
   but it still adds a **widget extension target** to the iOS build, so the failure mode that
   killed the NSE — a green build that crashes on launch, per store-readiness-plan and builds
   1077/1079 — applies here at larger scale. Cutting the NSE for that risk and then keeping a
   bigger target unexamined would be incoherent. The honest counter-argument is that this one may
   be worth real risk: it is the only item in the doc that *removes* notifications rather than
   adding them, and it is the most modern-feeling thing the app could ship. Three ways out:
   (a) build it and accept the risk deliberately, (b) hold it until the app is out of TestFlight
   and the runner/Xcode/`expo-modules-jsi` triangle is settled, (c) cut it and ship the Android
   ongoing notification alone, which needs nothing native and covers the platform that hasn't
   launched yet.
   **Recommendation: (b).** V2.4 is already last in the sequence, so holding it costs nothing that
   isn't already sequenced away, and it turns a risk decision into a timing one.
2. **Which phases are actually approved to build**, and in what order. §7 sequences them but
   nothing here is signed off. V2.0 and V2.1 are the two with no open dependencies.

## 10. Testing

Extends v1 §9's existing suites rather than starting new ones.

- **`format.test.ts`** — one case per new type and per new `expand` line, including the coalesced
  variants of F2/F3, the 140-char body boundary with `expand` present, and a case asserting no
  `expand` line restates its body.
- **`push_dispatch_triggers_test.sql`** — F1–F7 recipient sets (especially F4's "prior repliers
  minus author minus self"), F6's daily cap (the cap is the approval condition, so it needs a test
  that fails loudly if it regresses), and H1 firing from `promote_waitlist()` but **not** from a
  manual approve.
- **A new `share.test.ts`** — the consolidated share module is pure string-building and should be
  unit-tested, which none of the four current implementations are. Sport interpolation, the
  platform split, attribution params.
- **OG previews** — check every page type through a link-preview validator plus a real WhatsApp,
  iMessage and Slack send, since all three crop and size-limit differently. The 300 KB ceiling is
  the failure mode that produces no error, just a missing image.
- **Manual matrix** — v1's ~20-event checklist grows to ~30 and stays a per-release run on two
  physical devices. Inline reply (§5.4) needs both platforms, since iOS and Android surface the
  text field differently. If V2.4 proceeds, Live Activities cannot be exercised on a simulator at
  all and need their own line on that checklist.
